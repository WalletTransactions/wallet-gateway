# wallet-gateway

Единая точка входа для браузера: снаружи один origin (`wallet-gateway`), а
внутри маршрутизация по префиксу пути на настоящие сервисы. Решает то, что
раньше было костылём — "браузер не различает cookies по порту, работает
только на `localhost`" — по-настоящему: `session`/`refresh_token`, которые
ставит auth-сервис, больше не полагаются на порт-агностичность cookies,
потому что все запросы и так идут на один хост.

Таблица маршрутизации и собственное поведение шлюза (JWT-гейт, 502,
`X-Trace-Id`) — [`openapi.yaml`](openapi.yaml); контракты того, что реально
форвардится, — в openapi.yaml `google-auth`/`wallet-api`. Сервис отдаёт свою
спеку и сам: `GET /openapi.yaml`, `GET /docs` (Swagger UI) — эти два пути
обрабатывает сам гейтвей, НЕ проксирует (см. main.cpp — зарегистрированы до
catch-all `/{proxyPath}`); `/docs` каждого апстрима — по его прямому порту,
см. их README.

```
браузер ──> wallet-gateway (:8090, единственный origin)
                ├─ /auth/*          ──> auth-service    (google-auth, :8080)
                ├─ /api/reports/*   ──> wallet-report    (read-only, шареная БД, :8084)
                ├─ /api/* (прочее)  ──> wallet-api       (кошельки+синк, своя БД, :8082)
                ├─ /admin/*         ──> auth-service
                └─ всё остальное    ──> wallet-web (nginx, статика SPA, :8083)
```

Ровно то же самое в проде сделает **AWS ALB** с path-based routing правилами
на listener (см. обсуждение в чате) — этот сервис нужен, чтобы то же
поведение можно было проверить локально, без AWS.

## Login redirect — через гейтвей целиком, включая сам OAuth callback

Кнопка "Войти" на SPA ([wallet-web](https://github.com/WalletTransactions/wallet-web)) ведёт на относительный
`/auth/google` — гейтвей сам перенаправит на auth-service. Сам OAuth
callback Google тоже возвращает браузер СЮДА (`redirect_uri` =
`REDIRECT_URL` в `.env` google-auth, указывает на
`http://localhost:8090/auth/google/callback` — порт гейтвея, см. README
google-auth, "Через гейтвей, не напрямую"), а гейтвей прозрачно проксирует
`/auth/google/callback` на auth-service (тот же открытый префикс `/auth/*`,
без JWT-гейта) — код обмена/верификации в google-auth об этом ничего не
знает, `redirect_uri` для него просто строка. После логина google-auth
делает `302` на `/` — сюда же, на гейтвей, — тот отдаёт SPA, а она сама
дёргает `GET /auth/me`, чтобы узнать, что уже залогинена, и отрисовать
дашборд. Без единого ручного шага "откройте адрес гейтвея".

## Проверка JWT на входе (`/api/*`, включая `/api/reports/*`)

Гейтвей сам проверяет подпись и срок годности access-токена **только** на
`/api/*` (и `/sync/*`) — это чистый JSON REST, где 401 и так штатный ответ на
отсутствие токена (см. `wallet::require_auth` в wallet-api), так что гейтвей
просто отсекает то же самое чуть раньше, не тратя сетевой поход до бекенда
на заведомо мусорный запрос. `/api/reports/*` проверяется тем же гейтом, но
маршрутизируется на другой апстрим — `WALLET_REPORT_API_URL`, не
`WALLET_API_URL` (см. `find_route` в `main.cpp`, порядок проверки префиксов
важен: `/api/reports/` — ДО общего `/api/`, иначе тот перехватил бы первым).

**`/auth/*` и `/admin/*` намеренно НЕ защищены на этом уровне:**

- `/auth/*` — это сам логин/refresh/logout (в т.ч. `GET /auth/me`, которым
  SPA проверяет, залогинен ли пользователь — если бы гейтвей требовал
  валидный токен на весь `/auth/*`, сам этот проверочный запрос от
  анонимного посетителя получал бы 401 от гейтвея, а не осмысленный 401 от
  google-auth). Закрыть весь префикс проверкой токена означало бы, что
  зайти вообще никто не сможет (нечем было бы получить первый токен).
- `/admin/*` — там уже есть своя корректная логика в `admin.cpp`
  (незалогиненного редиректит на `/`, залогиненного не-админа встречает
  красивой 403-страницей). Грубый `401` от гейтвея тут не добавил бы
  безопасности, а UX бы ухудшил.

### Почему не дублируем авторизацию, только валидацию

Гейтвей проверяет ровно одно: "это настоящий, неподделанный, ещё не
истёкший токен" (подпись + `exp`). Он **не** решает, что именно этому
пользователю можно — это остаётся целиком на бекенде (`wallet.cpp` в
wallet-api, `admin.cpp` в google-auth). Так сделано осознанно:

- Дублировать бизнес-правила в двух местах (гейтвей + сервис) — верный
  способ рассинхронизировать их при следующей правке одного без другого.
- Гейтвей ничего не знает о ресурсах (чей это кошелёк) — это доменная
  логика, ей место рядом с данными, а не в универсальном роутере.
- Токен долетает до бекенда **как есть** (cookie/заголовок не подменяются,
  никаких "доверенных" `X-User-*` заголовков от гейтвея нет) — то есть
  бекенд всё равно сам всё перепроверяет. Это специально: если бы гейтвей
  подменял токен на доверенный заголовок, а бекенд ему слепо верил, прямой
  запрос в обход гейтвея (сейчас `google-auth`/`wallet-api` всё ещё слушают
  свои порты напрямую) подделал бы личность без единой подписи. Так
  безопасно ровно до тех пор, пока бекенды не закрыты файрволом от прямых
  обращений — сейчас это не так, поэтому "доверенным заголовкам" тут не
  место.

## Как убрали общий секрет

~~Раньше был общий `JWT_SECRET`~~ — теперь auth-сервис подписывает
access-токены приватным RSA-ключом (RS256), а гейтвей проверяет их по
**публичной** части, которую сам же auth-сервис отдаёт всем желающим на
`GET /.well-known/jwks.json` (см. его README). В `.env` гейтвея теперь
никакого секрета вообще нет — только `AUTH_SERVICE_URL`.

Кэшируется в памяти при старте (см. `src/util/jwks.hpp` — тот же файл
слово в слово, что в wallet-api) и обновляется заново, если встретился
незнакомый `kid` — например, после ротации ключа на auth-сервисе.

## Тело запроса и pre_routing_handler (баг, который тут был)

cpp-httplib вызывает `pre_routing_handler` **до** чтения тела запроса —
специально, чтобы отказ на входе (например, неудачная авторизация) не
заставлял буферизовать потенциально большое тело зря. Если бы сам проксинг
(`out.body = req.body`) делался прямо в `pre_routing_handler` — а раньше
именно так и было, — `req.body` там был бы ВСЕГДА пустой, независимо от
метода: любой `POST`/`PUT`/`PATCH` с реальным телом (например, `POST
/api/wallets`) долетал бы до апстрима с пустым body, а тот отвечал `400
некорректный JSON`. Поэтому сейчас разделено: `pre_routing_handler`
(`handle_pre_routing` в `main.cpp`) — только грубый JWT-гейт, отвечает сам
лишь при 401; сам проксинг (`handle_proxy`) зарегистрирован как обычные
`Get(".*", ...)`/`Post(".*", ...)`/... — их httplib вызывает уже ПОСЛЕ
чтения тела. См. подробные комментарии в `main.cpp`.

## Версия

`GET /version` (тег `self` — своя, не апстримов, ручка, тот же приём, что и
`/healthz` выше), строка лога при старте и `build_info` в `GET /metrics` —
общая схема для всех 4 C++-сервисов проекта, см. README google-auth,
"Версия" (файл `VERSION` + git-хэш, откуда берутся, как проставляются на
билде — код и приём идентичны).

## Конфигурация

```bash
cp .env.example .env
```

- `AUTH_SERVICE_URL` / `WALLET_API_URL` / `WALLET_REPORT_API_URL` /
  `WALLET_WEB_URL` — адреса реальных сервисов. Никакого общего секрета в
  конфиге — гейтвей сам тянет публичный ключ auth-сервиса с
  `AUTH_SERVICE_URL + /.well-known/jwks.json` (см. "Как убрали общий секрет"
  выше).
- `PORT` — порт самого гейтвея (по умолчанию `8090`) — **это и есть** тот
  адрес, который стоит открывать в браузере вместо `8080`/`8082`/`8083`.

## Сборка и запуск

```bash
cmake -B build
cmake --build build --config Release
build/Release/wallet_gateway.exe   # Windows; на Linux — build/wallet_gateway
```

Порядок запуска: сначала auth-service, wallet-api, wallet-report и wallet-web,
потом гейтвей (сам он ничего не поднимает, только проксирует). Дальше в
браузере — `http://127.0.0.1:8090/`, не `8080`/`8082`/`8083`/`8084`.
